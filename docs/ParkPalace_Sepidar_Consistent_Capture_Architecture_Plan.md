# طرح معماری برداشت مقطعی سازگار (Consistent Point-in-Time Capture Plan)

> **وضعیت سند:** طرح پیشنهادی و ارزیابی فنی معماری (Architecture Proposal & Evaluation)  
> **مرجع سیستم:** سامانه پارک‌پالاس (ParkPalace CRM) و پایگاه‌داده عملیاتی سپیدار (`Sepidar01`)  
> **محدودیت و خط قرمز قطعی:** این سند صرفاً یک **طرح مهندسی پیشنهادی** جهت بررسی DBA و کارفرماست؛ هیچ‌گونه دستور تغییر ساختار، تنظیمات یا `ALTER DATABASE` روی پایگاه‌داده عملیاتی سپیدار اجرا نشده و نخواهد شد.

---

## ۱. صورت مسئله و چرایی نیاز به برداشت سازگار (Problem Statement)

در پایلوت محدود انبار مواد اولیه (انبار ۱، سال مالی ۱۴۰۵)، سامانه CRM نیازمند خواندن دو دسته داده مرتبط با کالاهاست:
1. **موجودی مقطعی در انبار (`INV.ItemStock`):** میزان موجودی فیزیکی و ورودی/خروجی تجمعی کالا.
2. **کاردکس گردش اسناد (`INV.InventoryReceiptItem` و `INV.InventoryDeliveryItem`):** ردیف‌های رسیدها و حواله‌های انبار.

### علل رد قطعی روش‌های بدون ایزولاسیون:
- **روش بدون قفل (`NOLOCK / READ UNCOMMITTED`):** منجر به خواندن داده‌های کثیف (Dirty Read) و اسناد تراکنش‌نیافته یا در حال Rollback می‌شود.
- **روش سنتی `READ COMMITTED` پیش‌فرض:** به دلیل استفاده از قفل‌های اشتراکی ردیف/صفحه (`S-Lock`)، اگر کاربری در سپیدار در حال ثبت سند باشد مسدود می‌شود؛ یا برعکس، خواندن CRM با نوشتن انباردار دچار بن‌بست (Deadlock) می‌گردد. همچنین به دلیل عدم وجود ایزولاسیون تراکنشی بین کوئری موجودی و کوئری گردش‌ها، ممکن است سندی پس از خواندن موجودی و قبل از خواندن گردش‌ها ثبت شود که در نتیجه «موجودی» با «مجموع گردش‌های کاردکس» ناهمخوان خواهد شد (Non-repeatable Read / Phantom Rows).
- **رد قطعی کنترل `MAX(ID)`:** استفاده از `READ COMMITTED` و بررسی `MAX(ID)` اسناد در ابتدا و انتهای خواندن به عنوان تضمین سازگاری، **کاملاً مردود و نامعتبر است**؛ زیرا `MAX(ID)` صرفاً ایجاد رکوردهای جدید با شناسه بالاتر را کشف می‌کند و نسبت به هرگونه ویرایش مستقیم مقادیر (`UPDATE`)، حذف اسناد (`DELETE`) یا تغییر وضعیت اسناد موجود پیشین کاملاً نابیناست.

تنها راهکار تضمین‌شده موتور SQL Server برای دستیابی به تصویر منسجم و هم‌زمان (Point-in-Time Consistent View) بدون ایجاد هیچ‌گونه قفل اشتراکی، استفاده از **سطح ایزولاسیون Snapshot** است.

## ۲. پیش‌نیازهای فنی فعال‌سازی Snapshot Isolation در SQL Server

### ۲.۱. بررسی وضعیت فعلی پایگاه داده
در پایگاه‌داده `Sepidar01` وضعیت تنظیمات مرتبط به شرح زیر است:
- `snapshot_isolation_state = 0 (OFF)`
- `is_read_committed_snapshot_on = 0 (OFF)`

### ۲.۲. تمایز حیاتی بین دو گزینه اسنپ‌شات
SQL Server دو مکانیزم مبتنی بر نگارش سطر (Row Versioning) دارد:
1. **`READ_COMMITTED_SNAPSHOT` (RCSI):** سطح ایزولاسیون پیش‌فرض دیتابیس را به Snapshot تغییر می‌دهد.  
   ❌ **ممنوع برای پایلوت:** این گزینه ممکن است رفتار تراکنشی، مفروضات کدهای داخلی سپیدار و منطق قفل‌گذاری خوش‌بینانه/بدبینانه ERP را تغییر دهد و ریسک رفتاری ناشناخته ایجاد کند.
2. **`ALLOW_SNAPSHOT_ISOLATION`:** قابلیت Snapshot را صرفاً برای نشست‌هایی (Sessions) که به طور صریح دستور `SET TRANSACTION ISOLATION LEVEL SNAPSHOT` صادر کنند فعال می‌سازد.  
   ✅ **گزینه مورد بررسی:** تراکنش‌های پیش‌فرض سپیدار بدون کوچک‌ترین تغییری به روش سنتی `READ COMMITTED` خود ادامه می‌دهند و تنها نشست ریدر CRM از قابلیت ایزولاسیون نگارش بهره‌مند می‌شود.

### ۲.۳. نیازمندی‌های سخت‌افزاری و پیکربندی `tempdb`
- **فضای ذخیره‌سازی tempdb:** دیسک میزبان `tempdb` باید حداقل دارای ۲۰ تا ۳۰ درصد فضای آزاد با سرعت I/O مناسب (ترجیحاً SSD/NVMe) باشد.
- **پیکربندی فایل‌های tempdb:** تعداد فایل‌های داده‌ای (`.ndf`) tempdb ترجیحاً باید برابر با تعداد هسته‌های منطقی پردازنده (تا سقف ۸ فایل) با اندازه رشد اولیه یکسان تنظیم شده باشد تا از گلوگاه‌های تخصیص صفحه (PFS/GAM contention) جلوگیری شود.

## ۳. بررسی سازگاری و اثر عملیاتی بر نرم‌افزار سپیدار

### ۳.۱. عدم ادعای «نبود هرگونه اثر عملیاتی»
فعال‌سازی `ALLOW_SNAPSHOT_ISOLATION` رایگان نیست و اثرات زیر را به موتور پایگاه‌داده تحمیل می‌کند:
1. **سربار فضایی ردیف‌ها (Row Overhead):** به انتهای هر سطری که توسط کاربران سپیدار ویرایش (`UPDATE`) شود، یک برچسب نگارش ۱۴ بایتی (Row Version Pointer) افزوده می‌شود.
2. **تولید نگارش در `tempdb` (Version Store Generation):** هرگونه تغییر در جداول دیتابیس (شامل اسناد انبار، فاکتورها، حسابداری و ...) باعث کپی نسخه قدیمی سطر در Version Store دیتابیس `tempdb` می‌شود، فارغ از اینکه CRM در حال خواندن باشد یا خیر.
3. **سربار CPU در پاک‌سازی نگارش‌ها:** فرآیند پس‌زمینه Ghost Cleanup و Version Store Cleanup موظف است نگارش‌های قدیمی که دیگر هیچ تراکنش فعالی به آنها نیاز ندارد را پاک کند.

### ۳.۲. مزیت سازگاری برای کاربران انبار
- کوئری خواندن CRM تحت تراکنش Snapshot، **هیچ قفل اشتراکی (S-Lock) روی ردیف‌ها یا صفحات اسناد انبار (`INV.InventoryReceiptItem` و `INV.InventoryDeliveryItem`) قرار نمی‌دهد**.
- در نتیجه، عملیات انبارداران (ثبت ورود، ثبت خروج، ویرایش رسید) توسط CRM به هیچ عنوان مسدود (Block) نمی‌شود و احتمال بروز Deadlock به صفر می‌رسد.
- ریدر CRM تصویری پایدار از وضعیت انبار در دقیقه‌و‌ثانیه شروع تراکنش می‌بیند، حتی اگر در همان لحظه انبوهی از اسناد جدید توسط اپراتورها در حال درج باشد.

## ۴. طرح اندازه‌گیری تجربی بار و فضای لازم (بدون تخمین حدسی)

به جای تخمین‌های فرضی و بدون شاهد (مانند «کمتر از ۱۰۰ مگابایت»)، بار واقعی سیستم باید با استفاده از رویه‌های پایش استاندارد SQL Server و نماهای مدیریت پویا (DMVs) اندازه‌گیری شود.

### ۴.۱. کوئری پایش وضعیت دیسک و مصرف فضای `tempdb`
```sql
-- بررسی میزان فضای تخصیص‌یافته و آزاد tempdb به تفکیک مصرف
SELECT 
    SUM(unallocated_extent_page_count) * 8 / 1024 AS [FreeSpace_MB],
    SUM(version_store_reserved_page_count) * 8 / 1024 AS [VersionStore_MB],
    SUM(user_object_reserved_page_count) * 8 / 1024 AS [UserObjects_MB],
    SUM(internal_object_reserved_page_count) * 8 / 1024 AS [InternalObjects_MB]
FROM tempdb.sys.dm_db_file_space_usage;
```

### ۴.۲. کوئری اندازه‌گیری مصرف Version Store به تفکیک پایگاه داده
```sql
-- پایش سهم دقیق دیتابیس سپیدار از فضای Version Store
SELECT 
    DB_NAME(database_id) AS [DatabaseName],
    reserved_page_count * 8 / 1024 AS [VersionStoreSpace_MB]
FROM sys.dm_tran_version_store_space_usage
WHERE DB_NAME(database_id) = 'Sepidar01';
```

### ۴.۳. کوئری پایش تراکنش‌های اسنپ‌شات فعال و طول عمر آن‌ها
طولانی شدن زمان باز بودن تراکنش اسنپ‌شات مانع از پاک‌سازی Version Store می‌شود:
```sql
-- بررسی تراکنش‌های اسنپ‌شات فعال و سن آن‌ها
SELECT 
    transaction_id,
    session_id,
    elapsed_time_seconds,
    first_snapshot_sequence_num,
    max_version_chain_traversed
FROM sys.dm_tran_active_snapshot_database_transactions
ORDER BY elapsed_time_seconds DESC;
```

### ۴.۴. برنامه اجرای آزمایشی اندازه‌گیری (Staging Evaluation)
1. فعال‌سازی آزمایشی در محیط تست / Backup سرور با بار کاری مشابه به مدت ۴۸ ساعت.
2. لاگ کردن مصرف `VersionStoreSpace_MB` در فواصل ۵ دقیقه‌ای در ساعات اوج ثبت اسناد.
3. استخراج منحنی حداکثر مصرف دیسک و نرخ تولید نگارش بر ثانیه (`Version Generation rate KB/s`).

## ۵. معیارهای توقف اضطراری (Circuit Breakers / Abort Criteria)

در صورت پیاده‌سازی و اجرای عملیاتی در آینده، تدابیر توقف خودکار باید بدون وقفه برقرار باشند:

| ردیف | شاخص پایش (Metric) | آستانه توقف اضطراری (Abort Threshold) | اقدام خودکار سامانه / DBA |
| :---: | :--- | :--- | :--- |
| ۱ | فضای آزاد دیسک tempdb | کمتر از ۲۰٪ کل فضای دیسک یا کمتر از ۲ گیگابایت | توقف فوری خواندن CRM و صدور هشدار دیسک |
| ۲ | طول عمر تراکنش ریدر CRM | بیش از ۳۰ ثانیه (`Reader Timeout = 30s`) | قطع نشست ریدر (`KILL session`) برای جلوگیری از تورم نگارش‌ها |
| ۳ | تأخیر دیسک tempdb (`I/O Latency`) | انتظار `PAGEIOLATCH_SH` یا `EX` بیش از ۲۵ میلی‌ثانیه | توقف عملیات همگام‌سازی تا تثبیت I/O سرور |
| ۴ | انباشت نگارش‌ها (`Version Accumulation`) | نرخ پاک‌سازی کمتر از نرخ تولید برای بیش از ۱۵ دقیقه متوالی | اعلام هشدار و بررسی تراکنش‌های معلق سیستم |
| ۵ | خطای ناسازگاری زمان‌بندی | هرگونه تداخل با فرآیند پشتیبان‌گیری شبانه سپیدار | لغو برداشت مقطعی در پنجره Backup |

## ۶. روش اجرای فعال‌سازی و دستورالعمل بازگشت تنظیمات (Rollback Procedure)

هرگونه تغییر باید منحصراً توسط DBA رسمی کارفرما انجام گیرد.

### ۶.۱. شرایط فعال‌سازی امن (Maintenance Window Activation)
اجرای دستور تغییر در ساعات غیرفعال انبار (مثلاً ساعت ۲۳:۰۰ شب) که هیچ تراکنش بازی روی دیتابیس وجود ندارد:
```sql
-- بررسی عدم وجود تراکنش باز روی دیتابیس قبل از تغییر
IF NOT EXISTS (
    SELECT 1 FROM sys.dm_tran_database_transactions 
    WHERE database_id = DB_ID('Sepidar01')
)
BEGIN
    ALTER DATABASE [Sepidar01] SET ALLOW_SNAPSHOT_ISOLATION ON;
    PRINT 'Snapshot Isolation enabled successfully.';
END
ELSE
BEGIN
    PRINT 'Cannot alter database: Active transactions exist. Aborted.';
END
```

### ۶.۲. دستورالعمل بازگشت سریع (Instant Rollback)
در صورت بروز هرگونه اختلال در عملکرد سرور، کندی یا کمبود فضا در tempdb، مدیر پایگاه‌داده می‌تواند بلافاصله با دستور زیر وضعیت را به حالت قبل بازگرداند:
```sql
-- گام ۱: قطع کلیه تراکنش‌های اسنپ‌شات خواننده CRM
-- (توسط DBA شناسایی و خاتمه داده می‌شود)

-- گام ۲: خاموش کردن قابلیت اسنپ‌شات روی دیتابیس
ALTER DATABASE [Sepidar01] SET ALLOW_SNAPSHOT_ISOLATION OFF;

-- گام ۳: تأیید بازگشت تنظیمات
SELECT name, snapshot_isolation_state_desc 
FROM sys.databases 
WHERE name = 'Sepidar01';
```

پس از اجرای بازگشت، موتور SQL Server بلافاصله ثبت سوابق نگارش در `Version Store` را متوقف کرده و با پایان آخرین تراکنش فعال، فضای اشغال‌شده در `tempdb` توسط فرآیند Cleanup آزاد می‌گردد.
