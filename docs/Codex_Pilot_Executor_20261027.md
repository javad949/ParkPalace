# Local transactional pilot executor — 2026-10-27

## Implementation

`InventoryPilotExecutor` creates a dedicated SQL Server context for each operation. It is deliberately not registered in DI and has no HTTP route, scheduler or production configuration changes.

- Preview and execution call the same `InventoryPilotPlanner.Build`.
- Execution re-reads warehouse, item mappings, base units and inventory under a serializable transaction, and requires the exact approved plan hash.
- Captures older than ten minutes are rejected; source fiscal provenance still requires the capture reader described below.
- A run ID cannot be reused after its audit event is committed.
- Snapshot/movement changes and the journal are committed together. Actual inserted IDs and SQL rowversions are recorded after SaveChanges, before transaction commit.
- The journal stores before and after values, the run ID, actor, plan hash and manifest hash in existing AuditEvents. No schema change is needed.
- Rollback uses the recorded IDs and compares the entire recorded after state, including rowversion, before reverting or deleting. Conflicting rows are preserved and counted. A rollback can run once; preserved conflicts require a separate reviewed decision.
- No material/catalog changes, checkpoint updates or global `InventorySyncJobs.Success` records are created. A limited pilot must not falsely mark every item healthy. Recommendations are not regenerated by this executor.

## Scope and limitations

The generic live-sync guard remains in place. No new service is reachable from the running app.

Still pending: an approved exact item manifest; a read-only source capture reader that pins and verifies fiscal scope; tests of genuinely simultaneous sessions/deadlocks and cancellation; a UI/report for partial-pilot health; production deployment review. The planner currently supports only the first exact-KG pilot and stops on uncertain legacy provenance.

The movement lookup is currently global to respect the existing global unique SourceMovementKey index. Serializable reads can lock a broad range; measure and narrow this safely before scheduling any production run.

No production host, Sepidar, PDC or production database was contacted. Test databases use a hard-coded localhost host and unique `PP_CodexPilot_*` names; cleanup targets only those generated names. Tests do not load appsettings.

## Build observations

The first Debug build encountered DLLs locked by an existing local app. That app was not stopped. Tests were rebuilt under the separate `CodexPilot` configuration.

NuGet's cached audit emitted NU1903 warnings for the existing Microsoft.AspNetCore.Authentication.Negotiate 8.0.13 dependency. No package upgrade or deployment was performed. Existing platform/nullability warnings also remain.
